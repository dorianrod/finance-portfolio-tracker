## Méthode reproductible

Les cinq arbres Git complets du dashboard sont extraits dans des répertoires temporaires. Les sources, contrats, imports, tests et catalogues de chaque révision restent ceux de cette révision. Seuls la configuration ESLint actuelle, ses règles et son script de fingerprint sont injectés. Les règles sont figées une fois pour toute l’expérience. Chaque lint démarre dans un processus neuf, sans cache et sans autofix. Les répertoires temporaires sont supprimés après exécution.

Un contrôle préalable exécute aussi **les règles d’origine sur l’arbre d’origine** : zéro diagnostic. Aucun échec de parsing ou de résolution de projet n’est accepté comme un résultat de couverture. Le lint porte sur `src`, tests compris ; les exemptions de production des règles restent actives. Les tests ne sont pas exécutés dans les arbres historiques.

Même installation pour chaque état : ESLint **10.4.1**, TypeScript **6.0.3**, typescript-eslint **8.61.0**. Les dépendances n’ont pas changé dans ces quatre commits. Empreinte SHA-256 de la configuration et des modules de règles utilisés :

```text

```

Depuis `packages/dashboard`, avec ces commits présents dans l’historique local :

```bash
npm run audit:eslint-history -- --output /tmp/finance-eslint-history.json
node scripts/summarize-eslint-history.mjs /tmp/finance-eslint-history.json /tmp/finance-eslint-coverage.json
```

Le premier JSON contient les diagnostics détaillés, leur gravité, les révisions complètes et les versions. Le second relie chaque constat aux lignes historiques explicitement recherchées dans [eslint-history-cases.json](scripts/eslint-history-cases.json). Une preuve absente provoque une erreur ; une autre erreur dans le même fichier ne suffit pas à déclarer le constat détecté.

## Contrôles livrés et migrations

- `no-complex-component-calculation` suit les variables locales immuables et leurs alias. Il groupe les champs calculés d’un objet retourné par `map`/`flatMap` et les propriétés géométriques d’un élément JSX. Le seuil reste deux opérations ; les petites expressions indépendantes restent autorisées. Il évite de compter deux fois une même dérivation ou de suivre des clés d’objet comme des variables.
- `no-inline-format-fallback` suit les alias booléens et les gardes `&&`/`||` sur la valeur formatée. Il couvre aussi les wrappers TS de domaine, les imports relatifs et les namespaces. Les conditions métier et les branches structurelles restent distinctes du formatage.
- `no-helper-context-params` suit la provenance des formatters, traductions et clients de contexte, y compris les alias, objets, namespaces et callbacks qui capturent un formatter. Les signatures exportées annotées sont aussi contrôlées. Les résultats déjà formatés et les callbacks métier ordinaires restent autorisés.
- `strict-boolean-expressions` est activé sur la production avec les nombres et nombres nullables interdits comme conditions implicites. Les contrôles explicites conservent les politiques zéro/absence ; les timestamps ne traitent plus l’époque zéro comme une absence.
- `public-api-first` couvre les classes déclarées ou expressions, les exports nommés/défaut et les listes d’exports. Aucun déplacement automatique ne franchit une initialisation de valeur susceptible de changer le comportement de la classe.
- `no-component-data-pipeline` extrait les réductions inline et les prédicats de collection composés. Les maps de rendu et recherches simples restent autorisés. Les interactions DOM internes du design system restent dans leurs primitives.
- `i18n-consistency` contrôle les alias de traduction et les évaluations immédiates au chargement d’un module. Les labels de configuration sont maintenant résolus à l’accès ; la validation Yup reçoit une fonction de message. Les tests vérifient un changement de langue après import.
- `no-ui-string-concat` contrôle l’assemblage de traductions et de valeurs formatées, les plages textuelles de présentation et les unités numériques dans les renderers. Les chaînes techniques (identifiants, classes, géométrie SVG) conservent des exceptions explicites. Les axes utilisent le formatter existant avec `decimals: 'auto'` pour préserver les fractions sans arrondi ajouté.
- `no-hardcoded-colors` couvre les valeurs d’apparence, les classes de palette et les écritures DOM de couleur, dont les métadonnées `theme-color` et leurs alias locaux. Les définitions de tokens et assets restent exemptées ; ce contrôle ne remplace pas un parseur CSS ou une analyse générale du DOM.

Tous ces contrôles sont activés en erreur. Les seuils de complexité 8/150 sont conservés, et aucune désactivation ESLint n’a été ajoutée à la production. La CI exécute désormais toute la suite, avec les tests de chaque règle et les régressions applicatives.

## Ce qu’ESLint seul ne remplace pas

La clé React `operation.account` peut être présente tout en étant répétée ; le lint ne connaît pas l’unicité réelle des comptes dans les opérations. De même, il ne peut pas déduire que le TRI glissant doit rester indépendant du TRI global. Ces comportements exigent les tests de régression déjà ajoutés aux audits.

La propriété d’une capacité métier et le classement sémantique d’un helper restent des décisions de revue. Le contrôle des clés de catalogue inutilisées reste `check-i18n-catalog.mjs`. Les branches de rendu qui changent aussi structure, ton ou visibilité sont volontairement conservées hors du contrôle simplifié des placeholders. Les paramètres de formatter non suivis peuvent nécessiter une deuxième exécution du lint après conversion du helper en hook.

Les règles font donc remonter simultanément la majorité des motifs des contre-audits, mais une exécution sans diagnostic n’est pas une preuve de conformité métier complète. La commande `eslint --fix` ne réalise pas les refactorings métier signalés par ces règles.
